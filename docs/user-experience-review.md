# 사용자 관점 점검

현재 공개 화면은 [raw-ecru.vercel.app](https://raw-ecru.vercel.app)의 읽기 전용 예제입니다. 검색·원문 읽기·관계 탐색은 브라우저에서 동작합니다. 공식 법령 API를 실시간 호출하거나 새 검토 문서를 생성하는 화면은 아닙니다. 아래 설명은 현재 코드와 실행 검증을 기준으로 합니다.

## 1. JSON을 Markdown으로 바꿔야 하나요?

필수는 아닙니다. 공식 API가 제공하는 XML·JSON에서 법령 식별자, 시행일, 조문과 출처를 직접 추출할 수 있습니다. 지식그래프도 이러한 구조화 데이터의 노드·관계로 만들 수 있고 MCP는 JSON 형태의 도구 결과를 전달합니다.

현재 공식 원문 저장은 XML·JSON 응답 파일과 SQLite 색인을 사용합니다. 공식 조문 그래프는 `law_graph.py`가 저장된 조문에서 필요한 노드를 구성합니다. 화면에서 읽기 편하도록 조문을 Markdown 문자열로 표시하지만, 전체 법령을 MD 파일로 변환하는 과정은 없습니다.

기관 규정집은 사람이 편집하고 Git으로 변경을 비교하기 위해 Markdown·YAML 메타데이터·Wiki-Link를 사용합니다. 따라서 **공식 원문은 원래 형식으로, 사람이 관리하는 기관 규정은 MD로** 유지하는 현재 구성이 적절합니다. 공식 원문을 MD로 내보내는 기능을 추가하더라도 읽기·편집용 파생본으로 취급하고 원본 식별자와 버전을 보존해야 합니다.

## 2. API를 호출하는데 본문 저장이 필요한가요?

한 번 검색하거나 최신 본문을 보여주는 기능은 API를 직접 호출하면 되므로 저장이 필수는 아닙니다. 다만 다음 업무에는 선택한 원문을 보관하는 편이 적절합니다.

| 업무 | 저장 이유 |
| --- | --- |
| 반복 조회 | 같은 본문을 외부 API에서 다시 받지 않음 |
| 개정 전후 비교 | 이전 버전과 새 버전을 함께 확보 |
| 검토 근거 재현 | 당시 사용한 조문·기준일·출처·해시를 확인 |
| 지식 스키마 변경 | 저장한 원문에서 새 색인과 관계를 재생성 |
| 제공자 접속 장애 | 마지막 확보 자료를 시점과 함께 제공 |

최신성 확인과 버전 보존은 함께 필요합니다. 저장됐다는 이유만으로 최신 법적 효력이 보장되지는 않습니다. 개정 여부를 확인하고, 결과가 확인된 시점과 미확인 범위를 표시해야 합니다. 신규 수집 버전을 보존하는 것과 모든 과거 연혁을 역으로 수집하는 것은 별도 작업입니다.

현재 공식 원문은 **0건**입니다. 2026-10-01 15:19 한국 시간에 법령·행정규칙·자치법규 각각 목록과 전문 표본 1건을 실제 조회했지만, 연결 점검은 응답을 메모리에서 분석하고 원문 저장소에 쓰지 않았습니다. [실제 API 점검 기록](api-connection-review.md)을 참고하세요.

## 3. 속도를 높이는 가장 효과적인 순서는 무엇인가요?

현재 단계에서는 PostgreSQL로 바꾸는 것보다 **반복되는 외부 조회·파싱·프로세스 시작을 줄이는 것**이 먼저입니다. 공개 예제 화면은 이미 정적 파일을 배포하고 브라우저에서 검색하므로 페이지를 사용할 때 법령 API 호출을 기다리지 않습니다.

운영 기능의 개선 순서는 다음과 같습니다. 아래 항목은 현재 구현 상태와 구분한 개선 권고입니다.

1. 필요한 법령을 선택해 저장하고, 법령 식별자·버전·조문·기준일을 키로 조회합니다. 최신성 확인은 별도 갱신 작업으로 수행하며 과거 버전 조회와 섞지 않습니다.
2. 기관 규정 그래프는 파일이 바뀔 때만 다시 파싱합니다. 현재 REST 요청의 `refresh()`와 MCP의 `_store()`는 자료가 그대로여도 전체 Markdown을 다시 읽습니다. 캐시를 도입할 때 파일 추가·수정·삭제와 인용 오류가 즉시 반영되는지 검증해야 합니다.
3. 외부 MCP 클라이언트는 하나의 stdio 연결에서 반복 호출합니다. 웹 MCP 브리지는 요청마다 새 작업 프로세스를 시작하므로 연결 재사용을 검토할 여지가 있습니다. 재사용 시 요청 격리·취소·시간 초과·종료 처리까지 검증해야 합니다.
4. 실제 원문이 누적된 다음 검색을 측정하고 전문 검색 색인을 추가합니다. 현재 SQLite의 이름·버전·시행일 색인은 있지만, 대규모 본문 검색의 전문 검색 색인은 없습니다. 여러 사용자와 동시 쓰기가 늘면 PostgreSQL과 전문 검색을 검토합니다.

2026-10-01 16:00 한국 시간의 로컬 측정은 다음과 같습니다. 아래 값은 중앙값이며 같은 합성 예제 규정을 사용했습니다.

| 처리 | 표본 수 | 소요 시간 |
| --- | ---: | ---: |
| 예제 12개 문서·31개 관계 전체 다시 읽기 | 20 | 9.126 ms |
| 이미 메모리에 있는 그래프 조회 | 100 | 0.048 ms |
| 웹 MCP 브리지의 새 프로세스 포함 조회 | 5 | 494.112 ms |
| 같은 stdio 연결에서 반복 MCP 조회 | 20 | 17.282 ms |

두 MCP 경로는 같은 3개 노드·3개 관계를 반환했습니다. stdio 최초 연결에는 별도로 455.236 ms가 들었습니다. 이 표본에서 반복 호출은 약 29배 차이가 있었으므로, 웹 MCP의 프로세스 시작 비용을 먼저 줄이는 것이 유력합니다. 지속 연결의 데이터 캐시와 전체 파일 재파싱은 별개의 개선이며 현재 코드에 적용하지 않았습니다. 요청 격리와 취소·정리 정책을 유지하도록 설계해야 합니다.

추가로 합성 Markdown 1,000개를 메모리에서 다시 파싱하는 데 224.133 ms(5회), 임시 SQLite의 합성 원문 500건에서 식별자로 상세 조회하는 데 0.416 ms(30회)가 들었습니다. 두 표본의 자료와 처리 범위가 다르므로 데이터베이스 간 성능 비교가 아닙니다. 임시 자료는 정리했고 공식 원문 저장 건수는 변경하지 않았습니다. [측정 기록](performance-evidence.json)에 표본 수와 범위를 보관합니다.

이번 점검에서 외부 법령 API의 처리 시간, 전국 원문 규모와 동시 사용자 부하는 측정하지 않았습니다. 작은 예제의 로컬 결과를 운영 서비스의 응답 시간으로 해석하면 안 됩니다.

## 4. 대시보드에서 무엇을 쉽게 구분해야 하나요?

첫 화면에서 **API 표본 검증**, **실제로 저장한 원문**, **이 화면에서 사용할 수 있는 기능**을 나누어 보여줍니다. API 표본 성공을 전체 법령 확보나 법적 적합성 검증으로 표현하지 않습니다. 규정 찾기 → 관계 보기 → 변경 영향 보기 → 검토 문서 읽기의 흐름으로 예제를 안내합니다.

7개 메뉴와 기존 검색·조문 선택·관계 탐색·영향 분석 예제·문서 7개 읽기 기능을 유지합니다. 공식 법령별 미확인 버전·항/호·첨부파일 표시도 유지합니다. 본문과 상태 라벨의 글자 크기·대비 및 작은 화면의 배치를 개선합니다.

## 5. 봇은 제 기능을 하나요?

현재의 5개 봇은 `PackageWorkflow`의 처리 단계입니다. 서로 독립적으로 대화하는 다중 LLM 에이전트는 구현되어 있지 않습니다.

| 단계 | 실제 처리 | 현재 한계 |
| --- | --- | --- |
| 절차 총괄 | 검토 순서와 산출물 흐름 구성 | 기관별 결재·공포 시스템 실행 없음 |
| 지식 조사 | 로컬 관계와 저장된 공식 근거 조회 | 공식 원문 0건, 적용법 전체 판단 불가 |
| 비전 | 별도 도구에서 연결된 모델로 이미지 분석 | 현재 OCR 모델 미연결; 워크플로는 기존 MD 서식 사용 |
| 입안 | 담당자 입력 또는 기본 검토 템플릿 사용 | 실제 LLM 입안은 모델 설정·연결 검증 필요 |
| 검증 | 인용 존재·조 번호·구조 검사, 오류 시 문서 생성 차단 | 법률 해석·위임 적법성을 보증하지 않음 |

그래프·영향 분석·대비표·검토 패키지 기능은 자동 검증했습니다. Vision의 `unavailable` 응답은 미연결 상태를 올바르게 알린다는 확인이며 OCR 성공을 의미하지 않습니다. 외부 모델의 모의 응답 테스트를 실제 모델 연결 성공으로 표현하지 않습니다.

## 6. 다른 사람이 MCP를 편하게 사용할 수 있나요?

로컬 MCP 클라이언트는 저장소와 Python·uv를 설치하고 stdio 설정을 등록하면 사용할 수 있습니다. 현재 도구는 관계 조회·변경 영향 분석·대비표·선택적 이미지 분석의 4개입니다. [MCP 연결 가이드](mcp.md)에 복사 가능한 JSON 설정과 도구 입력 예제를 제공합니다.

공개 Vercel URL은 웹 예제 주소이며 원격 MCP endpoint가 아닙니다. 타인이 URL 하나만 입력하는 원격 MCP 서비스는 아직 제공하지 않습니다. 이를 제공하려면 Streamable HTTP 전송, 사용자별 인증·권한과 접근 가능한 서비스가 필요합니다. 이번 작업은 운영 서버를 생성하지 않습니다.

공식 조회 도구의 `source_scope: "official"`은 저장된 원문을 조회합니다. OC만 넣어도 국가법령정보 API를 자동 호출해 원문을 채우는 기능은 아닙니다. 빈 저장소 응답과 외부 OCR 미연결 응답을 가이드에서 명확히 설명합니다.

## 검증 근거

- 백엔드 기존 테스트 168개 통과: 그래프·영향 분석·문서 생성 차단·원문 버전 보존·실제 stdio 및 HTTP→stdio 호출 포함.
- 배포 게이트웨이 테스트 17개 통과: 로그인·쿠키·원점 검사·요청 전달. 외부 서비스 응답은 모의 테스트입니다.
- MCP의 이번 실제 프로토콜 점검은 [MCP 사용 검증 기록](mcp-usability-evidence.json)에 기록합니다. 공개 화면의 과거 MCP 실행 기록과 구분합니다.
- 공개 빌드의 브라우저 검증 통과: 7개 메뉴, 원문 12개·관계 31개·문서 7개, 데스크톱 1440px·모바일 390px에서 가로 넘침 없음. 추가로 체험 바로가기 8회, 검색 키보드 포커스와 관계도 글자 배치, 삭제 요청 문구가 없는 14개 화면을 확인했습니다. API·외부 요청과 런타임 오류는 0건입니다. 캡처는 생성하지 않았습니다.
- 실제 배포 확인 전에는 로컬 빌드 성공을 배포 완료로 간주하지 않습니다.
